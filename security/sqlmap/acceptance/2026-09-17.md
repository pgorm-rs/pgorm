# sqlmap control verification — 2026-09-17

**The full profile passes, against the build that ships.** All 117 scheduled
case-technique pairs were detected in their controls, no protected route
yielded a finding, the direct SQL security regressions passed in the same run,
and no declared exemption was falsified. 93 further pairs are declared
inapplicable with evidence, so all 210 cells are accounted for.

The counts are identical to the [2026-09-14 run](2026-09-14.md). The reason to
re-run was not the counts but the subject: that run, and every run before it,
scanned a `pgorm` linked against stock `prqlc 0.13.14` from crates.io rather
than the pinned fork.

`security/sqlmap/adapter` declares its own `[workspace]`, and cargo reads
`[patch.crates-io]` only from a workspace root, so the adapter silently
resolved the registry crate while the shipped library resolved the fork. The
difference is not cosmetic for this suite in particular: fork commit
`9023adad` changes how a SQL identifier is quoted, and identifier handling is
the one surface where injection in an ORM can live. The suite was therefore
reporting on a binary nobody ships. That is fixed — the adapter's lockfile now
resolves `git+https://github.com/necessary-nu/prql.git?rev=d6f2fa97…` — and
this is the first result describing the real configuration.

## What this does not claim

Everything the [2026-09-14 report](2026-09-14.md) declines to claim is declined
here unchanged, and is not restated: the six cases carrying no scheduled
technique, the inline-query exemption across all 35 cases, and the standing
assumption that some of the 93 exemptions are repairable rather than
structural.

Three things are specific to this run.

**It does not retroactively validate the earlier runs.** The 2026-09-14 result
stands as evidence about a binary linking stock prqlc. Since the identifier
quoting differs between the two, that report's silence is not transferable to
the shipped build; this one's is. The counts matching is a fact about the
suite, not a demonstration that the difference was immaterial.

**It says nothing about the smoke profile,** which cannot pass. Smoke scans at
level 2 / risk 1 and schedules `parameters`, whose control only sqlmap's level
3 boundaries can reach, so it ends with `Undetected controls: parameters-B`
every time. Measured both ways: at level 2 the control completes with 95
requests and zero findings where `select` and `pipeline-literal` each detect in
36, and the same case at level 3 passes on B, E, U, S and T. Tracked as
`sqlmap-smoke-unrunnable`.

**It is a local run, and CI has never produced one.** The sqlmap workflow has
executed once, the scheduled full profile on 2026-09-14, and it never reached
the scanner: it died in setup with `cannot update the lock file
security/sqlmap/adapter/Cargo.lock because --locked was passed to prevent
this`, published `NOT-RUN`, and exited. Regenerating that lockfile to carry the
prqlc patch incidentally repaired it, so the next scheduled run should scan —
and should be expected to fail on smoke until the profile above is fixed.
