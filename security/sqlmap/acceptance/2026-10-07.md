# sqlmap control verification — 2026-10-07

**The full profile passes on PostgreSQL 18.6, the first run of this suite on
anything but 16.13.** All 117 scheduled case-technique pairs were detected in
their controls. No protected route yielded a finding, and the direct SQL
security regressions passed in the same run, 17 of 17. No declared exemption
was falsified. 93 further pairs are declared inapplicable with evidence, so all
210 cells are accounted for. The identifiers profile, scanned next on the same
server and the same clean tree, also passes: 28 of 28 scheduled pairs detected,
38 declared inapplicable, and no protected route yielding a finding.

The counts match the [2026-10-05 run](2026-10-05.md). The subject does not. The
server moved from PostgreSQL 16.13 to 18.6, and 47 commits landed between that
run's revision, `ac5b4d5a`, and this one, `e2b92232`.

## What changed

**The server.** Both harnesses now start `postgres:18.6-bookworm` by its index
digest, the image pgorm-python's Docker wrapper already pinned (`e2b92232`).
One thing about 18 broke the fixture before any scan: the 18 image keeps its
data under `/var/lib/postgresql/18/docker`, and its entrypoint refuses to start
with anything mounted at `/var/lib/postgresql/data`, where this harness put its
anonymous volume. The volume now mounts at `/var/lib/postgresql`. Nothing else
in the harness, the manifest, the profiles or the fixture SQL changed, and no
control needed a new expectation. Error-based detection depends on
PostgreSQL's own error text reaching the page, and it fired on every scheduled
pair as it did on 16.13. The medians moved by fractions of a second.

**pgorm's grammar.** pgorm now parses with PostgreSQL 18's grammar through a
pinned fork of pg_query (`28fa2f64`), so the `sql!` macro, codegen's DDL path
and the identifier render oracle hold SQL to the grammar this server speaks.

**New constructs landed beside the scanned ones**: VIRTUAL generated columns
and SET/DROP EXPRESSION, named NOT VALID and NO INHERIT NOT NULL constraints,
NOT ENFORCED foreign keys and CHECKs, WITHOUT OVERLAPS keys and PERIOD foreign
keys, RETURNING's old and new rows and their renames, MERGE's BY SOURCE arms,
RETURNING and WITH body, the SQL/JSON query functions and constructors,
JSON_TABLE, `uuidv7()`, composite conflict targets, and ranges from Python.
None of them is a case in this manifest. Where they render a caller's name,
the commit that built them registered the position with the identifier render
oracle: 39 positions have joined it since the last run, among them RETURNING's
`OLD AS` and `NEW AS`, every JSON_TABLE column and path name, the WITHOUT
OVERLAPS and PERIOD columns, and each new constraint name.

What this run newly shows is that the same 117 controls fire against 18, and
the same protected routes stay clean, over a pgorm that grew all of that.

## The quiet

Both runs started on an awake machine below the load gate: 4.16 for the full
run and 4.68 for the identifiers run, with no disk cleaner running. A sampler
recorded the load average and busiest processes every ten seconds through both.
The power log records no sleep from 12:48 UTC, an hour and a half before the
first scan, to the end of the second.

The identifiers run stayed quiet throughout, peaking at 5.6 with no compiler
running. The full run did not. Compiles that were not this run's ran twice
during it: nine `rustc` processes at 14:39 UTC, and one to four from 14:47 to
14:51. The direct regressions were built beforehand and compiled nothing. The
load average peaked at 9.4 at 14:50:47. A Windows application running under
CrossOver held most of a core throughout both runs. Every timing control fired
anyway, so nothing in the verdict rests on that stretch having been quiet, but
the run was not as quiet as the 2026-10-05 one.

## What this does not claim

Everything the [2026-10-05 report](2026-10-05.md) declines to claim is declined
here unchanged: the inline-query exemption across all 35 cases, the standing
assumption that some of the 93 exemptions are repairable rather than
structural, and any claim about the 38 identifier pairs no sqlmap boundary
reaches, which belong to the identifier render oracle
(`tests/identifier_oracle/`, `[spec:pgorm:req:security.ident-oracle]`).

It does not claim PostgreSQL 16 or 17. The suite now runs on 18 only, and these
results say nothing about the releases before it.
