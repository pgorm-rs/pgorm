# sqlmap control verification — 2026-09-14

**The full profile has not passed.** 110 of 127 scheduled pairs passed; 16 came
back `invalid-control` and 1 `incomplete`. Ten of those seventeen are cells left
neither repaired nor exempted, four were measured on a loaded machine and cannot
be trusted either way, and two were predicted to fail. Nothing here closes
`sqlmap.acceptance`.

Three results are worth stating separately from the failure count, because they
are what the suite exists to establish and they are not in dispute:

- **Zero pairs came back `vulnerable`.** sqlmap found no injection in any
  protected route, and those routes exercise real pgorm APIs.
- **The direct SQL security regressions passed** against the same disposable
  database, in the same run.
- **`falsified_exemptions` is empty.** None of the 83 evidence-backed exemptions
  was contradicted by a technique actually firing against it.

That third point matters more than it looks. The exemption mechanism fails the
run if a pair it declared unreachable is detected, so an empty list is the
mechanism vouching for itself rather than an absence of checking.

did not change underneath it.

## What the rework achieved

The three reshaped controls work, and the improvement is measurable against the
2026-09-09 attempt, where every one of these cells was `invalid-control`:

| case | new control shape | now passes |
| --- | --- | --- |
| `update-value` | literal moved from the `SET` assignment into the `WHERE` | B, E, S, T |
| `cast` | `CAST` embedded in a `WHERE` so the unquoted type closes into a truth slot | B, E, U, S, T |
| `insert` | `INSERT … SELECT … WHERE` guarding on the value | B, E, U |

`insert` is also where the exemption mechanism proved itself. Its `U` cell had
been exempted on the argument that a DML statement offers no set-operation
position — true of `INSERT VALUES`, false of `INSERT SELECT WHERE`. The reshape
made `U` fire, the falsification check caught the now-false exemption, and it
was removed rather than kept.

## The seventeen failures

**Ten cells: neither repaired nor exempted.** These are the real outstanding
work, and they are an omission rather than a surprise.

`pipeline-projection-B`, `column-B`, `group-B`, `stored-identifier-B`,
`enum-B`, `enum-E`, `enum-U`, `enum-ddl-B`, `enum-ddl-E`, `enum-ddl-U`.

All are double-quoted identifier contexts. The reshape node examined each and
declined to change it, with a sound argument: error- and time-based payloads
carry no `<comment>` at level 3, so they can only fire in a genuine truth slot
and can never escape a double-quoted identifier. But declining to reshape is
only half a decision — each cell then needed either an evidence-backed
exemption or an accepted plan to fix it, and neither was recorded, so they
stayed scheduled and failed.

Every one of these ten was predicted by [CONTEXTS.md](../CONTEXTS.md), which
derived its predictions by reading the scanner's payload and boundary XML before
any scan ran. The non-timing failures matching the analysis exactly is an
independent validation of it.

**Four cells: measured under load, untrustworthy.**

`insert-S`, `insert-T`, `contains-T`, `stored-value-S`, plus `contains-S`
recorded `incomplete`.

The machine carried a load average between 6 and 14 from an unrelated
compilation throughout. Stacked-query and time-based blind both confirm by
timing, and the profile pins `--time-sec 1`, which is aggressive even on an idle
machine. `contains-S` is proven to be a load artifact: sqlmap said so in its own
words, reporting *"considerable lagging has been detected in connection
response(s)"*. `insert-S` argues the other way — it completed cleanly, return
code 0, 56 requests, 20.8s, with no lag warning — so it may be a genuine
non-detection. These four need a quiet machine before any verdict.

**Two cells: predicted to fail.** `enum-T`, `enum-ddl-T` — double-quoted
identifier, same argument as the ten above.

## What has to happen before this can pass

1. **Decide the ten identifier cells.** Either write exemptions to the same
   evidence standard as the existing 83, or take the trailing-slot reshape
   [CONTEXTS.md](../CONTEXTS.md) §7c suggests, accepting that it changes what
   those cases test and needs a matching exemption swap.
2. **Re-run the timing techniques on a quiet machine**, and consider raising
   `--time-sec` above 1. A longer sleep is still a sleep, so this tunes the
   harness without weakening what is detected.
3. **Fix the `source_unchanged` comparison** so identical content is not
   reported as a changed subject merely because HEAD moved.

## What this report does not claim

It does not claim pgorm is free of SQL injection. It records that a pinned
sqlmap at level 3 / risk 2, across 127 scheduled case-technique pairs, found no
injection in the protected routes, while 17 pairs could not be established at
all. Scanner silence on a pair whose control never fired is not evidence about
pgorm; it is an absence of evidence, which is why those pairs fail the run
rather than passing it.
