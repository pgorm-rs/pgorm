## What changed to get here

**Controls reshaped so a technique could reach them.** `update-value` moved its
literal from the `SET` assignment into the `WHERE`; `cast` embedded the `CAST`
in a `WHERE` so the unquoted type closes into a truth slot; `insert` became a
guarded `INSERT … SELECT … WHERE`; `enum` gained an enum-typed column to filter
on. Each protected twin moved with its control, so every pair still tests the
same SQL context on both sides.

**Exemptions given a retraceable standard.** `cases.json`'s `inapplicable` field
existed but was empty and read by no code. It now requires, per pair, a reason
plus evidence naming the payload definition, its qualifying `where`/`clause`
values, the boundary the context would need, and the section of
[CONTEXTS.md](../CONTEXTS.md) deriving it. Validation refuses a missing or stub
reason, a payload that does not define the technique, out-of-range values, or a
technique the case does not declare. Exempted pairs are excluded from scheduled
work, reported separately, and **never counted as passes**.

**The exemption mechanism self-polices.** A pair declared inapplicable that the
scanner nonetheless detects fails the run. That check earned its place: `insert`
`U` had been exempted on the argument that a DML statement offers no
set-operation position — true of `INSERT VALUES`, false once the control became
`INSERT … SELECT … WHERE`. The scan detected it, the check fired, and the false
exemption was removed rather than kept.

**A timing threshold that survives the suite's own load.** The profile pinned
`--time-sec 1`. At that threshold the full profile defeated itself: 254
invocations saturated the machine badly enough that the techniques confirming by
sleep stopped being observable, and cells failed that pass in isolation with
identical code. `time_sec` is now 3. A longer sleep is still a sleep, so this
tunes sensitivity rather than weakening what is detected.

## What this does not claim

**It does not claim pgorm is free of SQL injection.** It records that a pinned
sqlmap at level 3 / risk 2 found no injection in 117 case-technique pairs whose
controls it demonstrably *can* detect. Scanner silence on a pair whose control
never fired would prove nothing, which is why such pairs fail the run rather
than passing it.

**Six cases carry no scheduled technique at all** — `pipeline-projection`,
`schema`, `column`, `group`, `function` and `stored-identifier`. Every technique
is exempted for each, so the suite makes **no detection claim whatsoever** about
schema-name, function-name, or leading projected-identifier handling. The
reasons are evidenced and rest on the level-3 boundary catalogue, but the
consequence stands: these contexts are untested here, not tested-and-clean.

**Inline query (`Q`) is exempted in all 35 cases.** Its tests are REPLACE-only
(`where=3`), the sole boundary serving `where=3` carries an empty prefix and
suffix, and it confirms by grepping its own delimiters from the response body.
It therefore needs an unquoted, reflected projection. pgorm binds values and
quotes identifiers, so no faithful control in this suite exposes one.

**The exempted 93 are an argument, not a measurement.** They rest on reading the
pinned scanner's payload and boundary definitions. Three exemptions filed as
structural have already proved shape-dependent and been repaired, so the
standing assumption should be that some of the remaining 93 are repairable too,
not that the boundary has been found.
