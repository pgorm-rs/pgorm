# sqlmap control verification — 2026-09-24

**The full profile passes, against a pgorm that was rebuilt underneath it, and
for the first time at the timing threshold the profile declares.** All 117
scheduled case-technique pairs were detected in their controls, no protected
route yielded a finding, the direct SQL security regressions passed in the same
run, and no declared exemption was falsified. 93 further pairs are declared
inapplicable with evidence, so all 210 cells are accounted for.

The counts match the [2026-09-17 run](2026-09-17.md). The subject does not.
Between that run's revision, `27f2665b`, and this one, `9717c645`, 87 commits
landed, 36 of them in the query and rendering crates. They include a
restructuring of pgorm-query's identifier and rendering surface, a rewrite of
the only SQL lexer pgorm owns, and a re-pin of the prqlc fork. The scanner was
also, until this week, told something the profile did not say.

## Every earlier run scanned at one second

The full profile has declared `time_sec: 3` since `041e4412` on 2026-09-14.
That value never reached the scanner. `scanner_args` hardcoded `--time-sec 1`,
as the retired `harness.py` did before it, and `041e4412` changed only
`profiles.json` and the README. The run behind the [2026-09-17](2026-09-17.md)
report records `--time-sec 1` in every time-based `command.json`. Both the
[2026-09-14](2026-09-14.md) and [2026-09-17](2026-09-17.md) reports record
`time_sec 3`, and both are wrong about it. The 2026-09-14 report goes further,
crediting the change to three seconds with ending its load-induced timing
failures; its passing run used the same `--time-sec 1` as the failing one
before it, so what changed between them was the machine's state, not the
threshold.

Four other declared settings were ignored the same way — `concurrency`,
`retries`, `http_timeout_seconds` and `postgres_statement_timeout_seconds`.
Each happened to match its hardcoded value, so those runs did use what the
profile says, but only by coincidence: editing any of them in `profiles.json`
would have changed nothing. `77528abb` makes the profile govern. The harness
parses it into the settings the run uses, passes each to the scanner or the
fixture, refuses a profile that omits a setting or names one the harness does
not apply, and refuses timeouts that do not strictly increase from the timed
sleep to the scan deadline. `security.sqlmap.profiles` now says so and is at
`+2`.

This is therefore the first full run at `--time-sec 3`. The effect is visible
and confined to the timing techniques: the boolean, error and UNION control
medians are unchanged (1.5 s, 0.7 s, 1.6 s), while the stacked-query and
time-based control medians rose from 11.8 s to 31.8 s — a longer sleep,
confirmed as a sleep. A run that had been passing on a one-second signal now
passes on a three-second one.

## What changed in pgorm, and what this run newly shows

The run behind the 2026-09-17 report scanned `27f2665b`. This run scans
`9717c645`, 87 commits later. The changes that matter to an injection suite all
touch how pgorm turns a name or a value into SQL text, which is the surface the
suite exists to watch.

**The identifier vocabulary was rebuilt.** `Alias`/`Iden` are gone:
`Alias::new` became `Name::runtime`, the `Iden` trait became `SqlName`, and the
blanket `&str`/`String` conversions into a name were deleted, so a value now
reaches identifier position only through an explicit `Name::runtime`
(`213522c9`, `8495858a`). The adapter's own controls and protected routes were
rewritten to the new spelling, so every case that quotes an identifier —
`table`, `alias`, `order`, `enum`, `enum-ddl`, `column`, `graph-alias`,
`schema`, and the new smoke case `enum` — exercises the rebuilt path.

**The one SQL lexer pgorm owns was rewritten.** It had opened a string on a
MySQL/SQL-Server backtick or bracket and honoured a backslash escape inside
every quoted form; it now lexes only PostgreSQL's `'` and `"`, gives a
backslash meaning only inside `E'…'`, and hides the cursor fields a caller
could once drive off the end (`38b05af9`, `0f4f9634`). This lexer backs
`inject_parameters`, the API the `parameters` case drives.

**Quoting became a contract at every render site.** Three sites that emitted a
caller identifier unquoted now render through one policy (`cc6daf79`); a named
column type in a derive renders as a token rather than pasted between quotes
(`b494cd16`); a savepoint name is quoted as an identifier (`276dde57`); comment
text is written so a `standard_conforming_strings=off` session cannot reopen it
(`14fd59cf`); and a pipeline identifier no quoting can represent is refused
outright rather than handed to whichever prqlc the build resolves (`f48c6425`).
`custom` split into `raw` (verbatim `&'static str`) and `template` (validated,
arity-checked), so runtime data can no longer reach a verbatim render site
(`10a04f40`).

**The prqlc fork was re-pinned** from `d6f2fa97` to
`2ce6a2428ee850b1d1e16c41285f6ae7ee7fbe19` (`dfd59260`). The four added commits
change only PRQL shapes pgorm's pipeline builder never constructs — a
whole-row-star GROUP BY, literal keys in GROUP BY / DISTINCT ON — so a pgorm
query still compiles to the same SQL, but the pipeline cases
(`pipeline-literal`, `pipeline-bound`, `pipeline-sources`) now run against the
pinned compiler in both the adapter's lockfile and the workspace's.

What this run newly shows is that none of that opened an injection path. The
same 117 controls fire and the same protected routes stay clean under the
rebuilt identifier surface, the rewritten lexer, the render-site quoting
contract, and the re-pinned compiler. The 2026-09-17 result was evidence about
`27f2665b`; the identifier-quoting fork commit that report singled out has since
been superseded, the identifier types it described have been renamed, and the
lexer has been rewritten — so its silence is not transferable. This result is
evidence about `9717c645`, and the restructuring sits entirely between the two.

## What this does not claim

Everything the [2026-09-14 report](2026-09-14.md) declines to claim is declined
here unchanged, and is not restated: the six cases carrying no scheduled
technique (`schema`, `function`, `column`, `group`, `pipeline-projection`,
`stored-identifier`), the inline-query exemption across all 35 cases, and the
standing assumption that some of the 93 exemptions are repairable rather than
structural.

Two things are specific to this run.

**It corrects the timing threshold the earlier reports state.** The
2026-09-14 and 2026-09-17 documents record `time_sec 3`; both ran at
`--time-sec 1`. Those dated reports stand as written — they record what was
believed then — but their timing claim does not transfer, and this is the first
full run whose time-based controls confirmed on the declared three-second
sleep. That the counts are unchanged is a fact about which controls are
reachable, not a demonstration that the threshold was immaterial: it means the
one-second signal was already sufficient on a quiet machine, which is a weaker
statement than the reports made.

**It says which controls a loaded machine cannot measure.** Time-based and
stacked-query detection confirm by sleeping, and both are defeated by scheduling
jitter when the host is saturated. A first attempt at this run, on a machine
under a competing multi-core compile (load average above 30), lost
`tenant-or` and other cells on their false-positive timing check while
`delete` — which has byte-identical control SQL — passed, and the scanner itself
reported "considerable lagging has been detected in connection response(s)".
Those failures were environmental, not findings, and this run was taken on an
idle machine (load average below 3 throughout) where every scheduled control
fired. The suite's timing verdicts are only as trustworthy as the quiet of the
host that produces them.
