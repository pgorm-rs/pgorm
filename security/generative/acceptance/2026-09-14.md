### Parity — failed

15 of 15 declared families were attempted and parity was *established* for all
15, meaning each family's program ran to a decision on both sides. 12 are in
parity. `pipeline`, `relational` and `sets` diverge, and they diverge on one
check only:

```
selected API paths differ
  first:  pgorm::pipeline::Pipeline::all
  second: pgorm::pipeline::Pipeline::into_sql, pgorm::ConnectionTrait::query_raw
```

The observations and the final fixture state compare equal on all three; the
`final` step check is `equal`. The cause is in the harness, not the library:
`emit_rust_effects.compile_query` renders a pipeline through `into_sql` and
executes it with `query_raw`, because a generated pipeline has no concrete model
type to instantiate `Pipeline::all<M>` with. This is a known limitation of the
Rust emitter and is recorded as such rather than resolved by widening the check.
Until the emitter can reach `Pipeline::all`, parity for these three families
covers results but not the API path, and the component does not pass.

**No defect in this run is the already-filed `pipeline-renamed-column-order`.**
That was checked rather than assumed. Its signature is equal values under
identical column *names* in a different column *order*, and the oracle can see
it: `comparison.row_key` builds each row's fields as a list and `encoded` sorts
only dict keys, so field position survives into the compared key and a pure
reordering registers as `row multisets differ`. Every one of the 25

7 differ in a column *name*, 18 share an identical column sequence. The finding
remains open on its own retained reproducer; this run simply did not regenerate

### The three classes that match open findings

**Window frame and nullable count (10).** Nine use `Over` with `first` or
`last`; the tenth uses `count` in a grouped aggregate. Both halves of the filed
finding reproduce. For `runtime-101`, the subject returns `10` for the last
row's `last(...)` where the reference returns SQL NULL — the documented case of
an explicit `Over.rows(1, 1)` frame being dropped, leaving the empty trailing
frame to read a value it should not see. For `runtime-3716`, the subject counts
2 where the reference counts 1, which is `count(expr)` emitting `COUNT(*)` and
so failing to exclude a NULL. These are the two discrepancies
`security/generative/findings/window-semantics/` already isolates.

**Quoted derived column name (7).** Every one is a single output name differing
by exactly one quote: `derived49"` against `derived49""`, `window"` against
`window""`, `aggregate"` against `aggregate""`. Values match; only the result
metadata differs. That is `pipeline-quoted-output` exactly, now reproduced on
three name prefixes rather than the one in the filed report.

**Chained set-operation grouping (5).** All five chain `append` with `intersect`
(two also with `remove`). Four observe 8 rows where the reference expects 4, and
one observes 6 where the reference expects 3 — in every case exactly twice the
independently computed multiset. That is the filed unparenthesized
`UNION ALL … INTERSECT ALL` precedence defect.

### The four classes that are new

**Maximum-precision datetime parameter (7).** The subject fails before reaching
PostgreSQL with `ConstructionError: error serializing parameter 0`, while the
reference returns rows. In all seven the failing value is the same:
`9999-12-31 23:59:59.999999`, the maximum `timestamp` at full microsecond
precision, passed as a bound parameter. The same instant *without* microseconds
(`9999-12-31 23:59:59`) travels the literal path in the same programs and
succeeds, which locates the failure in parameter serialization rather than in
the value's representability. This is temporally adjacent to the stress
`FormatError`s but is not the same defect: that one is a snapshot-equivalence
question about trimmed trailing zeros on `time`, this one is a hard refusal to
encode a `datetime`.

**Decimal scale in a returned value (2).** The subject returns decimal `0` where
the reference returns `0.00`, both scalar and inside a decimal array. Numerically
equal, different scale. Whether the campaign's decimal comparison should be
scale-sensitive is a contract question the oracle currently answers "yes"; the
disagreement is real and is recorded rather than normalized away.

**Nested source loses its `FROM` entry (1).** `runtime-887` is rejected by
PostgreSQL with SQLSTATE `42P01`, `missing FROM-clause entry for table
"table_4"`, while the reference returns rows. The program joins, sorts, takes a
range and nests. This is kin to `pipeline-hidden-order` — both are nested
pipeline sources referring outward to something the enclosing scope no longer
exposes — but it is not the same defect: that one is `42703` on a *column* a CTE
never exposed, this one is `42P01` on a *table* absent from the `FROM` clause.

**Deduplicated, sorted, ranged pipeline picks different rows (1).**
`runtime-947` combines `distinct`, `sort` and `take_range`. The subject returns
one row (`p_score = 10`, `p_rank = 1`); the reference returns two
(`p_score = 30` and `p_score = NULL`, both `p_rank = 2`). Not a reordering and
not a formatting difference — a different set of rows selected.

## What this document does not claim

  does not replace full live coverage and does not prove that any ORM program is
  safe**, let alone all of them. No program in it opened a database connection
  and none was decided by an oracle. A million distinct program digests is a
  count of programs built, not of behaviours covered and not of programs checked.
- A construction count and an oracle decision are never summed.
- 173 of 430 full-matrix obligations were not discharged, spread across all 14
  obligation areas and concentrated in `value`, `pipeline`, `graph` and `crud`.
  Silence about them is absence of evidence, not evidence of absence.
- The parity component compares one generated program per family. It is not a
  general claim of Python/Rust execution or decoder parity.
- Passing sensitivity controls show the oracle could fail on this run. They do
  not bound what it would have missed.
